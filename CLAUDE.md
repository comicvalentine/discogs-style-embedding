# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Discogs Style Embedding: embeds Discogs music **styles** (subgenres) into vector space based on
co-occurrence, projects them to 2D/3D with UMAP, and renders an interactive explorable map published
to GitHub Pages at https://comicvalentine.github.io/discogs-style-embedding/.

There is no build system, package manifest, or pinned environment — dependencies are installed ad hoc
into a conda env (see `.vscode/settings.json`) and the site is static HTML deployed straight from `docs/`.

## Pipeline (run in this order)

Each stage reads/writes flat files under `embedding_data/` and `raw_data/`; there is no orchestration
script, so re-running the pipeline means invoking these manually in sequence.

1. **`raw_data/discogs_<date>_masters.xml.gz`** — monthly Discogs data dump from https://data.discogs.com/,
   gitignored (`*.xml.gz`) due to size. Must be downloaded manually before steps 2–3.
2. **`counter.py`** — streams the XML dump once, builds `single_counter`, `pair_counter` (style
   co-occurrence), and `max_genre_counter` (style → parent-genre distribution), pickled to
   `embedding_data/*_masters.pkl`. Flushes every 1M elements so it can resume/inspect progress.
3. **Embedding generation** (either or both):
   - `Word2Vec.py` — re-streams the same XML dump, treats each master's style list as a "sentence",
     trains `gensim.Word2Vec`, writes `embedding_data/Word2Vec/embedding_df_masters.csv`.
   - `Node2Vec.py` — builds a weighted directed graph from `pair_counter`/`single_counter` (edge weight =
     co-occurrence count / source style's popularity), trains `node2vec.Node2Vec` on it, writes
     `embedding_data/Node2Vec/embedding_df_masters.csv`.
4. **`umap_project.py`** — reduces either embedding to 2D and 3D via UMAP, writes
   `embedding_data/<algo>/embedding_df_masters_umap_{2,3}D.csv`. 2D uses `min_dist=0.5, spread=0.6`
   (tuned to reduce point overlap) and negates + rescales the x-axis (`adjust_coords`) purely for
   visual layout; 3D uses UMAP defaults. Run standalone — `visual.py` will call this itself as a
   fallback if the UMAP CSV is missing, but the fallback does not apply `adjust_coords` or the
   x-negation, so outputs differ slightly from running this script directly. Prefer running this
   script explicitly rather than relying on the fallback.
5. **`visual.py`** — the only entrypoint you actually run for output (`python visual.py [--search_type masters] [--algo Node2Vec|Word2Vec]`).
   `__main__` always builds one hardcoded algo's 2D map (D3, no plotly) plus its 3D map (legacy plotly) —
   edit the bottom of the file to change the algo or the baked-in focus style ("hardcore").

## Architecture: 2D is D3 (no plotly), 3D is still plotly

The 2D and 3D outputs are generated by two unrelated code paths in `visual.py` — **as of the D3 rewrite,
plotly is only a 3D-viewer dependency**; nothing in the 2D path touches it. This split is intentional and
temporary (3D wasn't worth a three.js rewrite yet) — don't assume both paths share behavior.

- **2D — `render_map_2d()`** reads the UMAP CSV, computes each style's main-genre + hover breakdown (from
  `max_genre_counter`) and a deterministic per-genre hue (`genre_hue_map()`, rotating from
  `GENRE_HUE_START=40`, kept away from the UI accent hue 176 defined in `web/map.css`), then fills
  `web/map.template.html` with the JSON payload, `web/map.css`, and `web/map.js` (simple `str.replace`
  on `__TITLE__` / `/*__STYLE__*/` / `/*__DATA__*/` / `/*__SCRIPT__*/` — not a templating engine) and
  writes the result as one self-contained HTML file to `docs/style_<algo>_masters_umap.html`. Editing
  `web/map.{css,js}` only takes effect after re-running `visual.py`.
  - `web/map.js` owns all interaction: `d3.zoom()` gives native wheel/trackpad zoom and click-drag pan on
    desktop and pinch/drag on touch — there is no mode-toggle button (the old Plotly build needed one
    because `dragmode` couldn't be pan and box-zoom at once; d3-zoom has no such restriction).
  - Marker/label size is kept constant on screen under zoom via the standard d3 trick: points sit in a
    `<g class="world">` that carries the zoom transform, while each point's own group carries a
    counter-scale (`scale(1/k)`) — see `render()`.
  - **Resizing must preserve the visible data-space window**, not the raw pixel transform — `resize()`
    reads the current center/zoom in data space with the *old* projector before recomputing, then
    re-derives an equivalent transform for the *new* projector. Skipping this (i.e. reusing the old
    zoom transform verbatim after a size change) strands every point outside the new viewBox — this was
    a real bug during development, triggered by any resize after interacting (e.g. rotating a phone).
  - The minimap is a second, independent static projection (`buildMinimap()`); only its viewfinder
    rectangle is recomputed per zoom event, by inverse-projecting the main map's visible corners.
- **3D — `visual()`** is the original Plotly path, unchanged, still paired with `post_script.js` (which
  assumes Plotly's DOM/`_fullLayout` internals and was written for the 2D UI that no longer exists —
  don't assume its search/legend/minimap logic still applies cleanly to the 3D output).
- **`docs/index.html`** is the outer shell (header/logo/title) that iframes the generated
  `style_Node2Vec_masters_umap.html` as `#plot-frame`. It is hand-maintained separately and not
  regenerated by any script — if you regenerate the Node2Vec 2D file, the filename it embeds must still
  match. Its own styling is hand-kept in sync with `web/map.css`'s tokens (paper/ink/accent colors, IBM
  Plex fonts) rather than sharing a stylesheet.

## Data contract between `visual.py` and `web/map.js`

`render_map_2d()` embeds one JSON object as `window.__MAP_DATA__` — `points` (`style`, `dim0`, `dim1`,
`genre`, `hover` as `[genreName, fraction]` pairs sorted desc), `genreHue` (genre name → hue degrees), and
`init` (`style`, `marginPct` — the fraction of the full data range visible in the boot camera). `web/map.js`
depends on these exact field names.

## Known naming inconsistencies

- 3D output files use a lowercase `_3d` suffix while 2D ones have no suffix at all
  (`style_Node2Vec_masters_umap.html` vs `style_Node2Vec_masters_umap_3d.html`).
- `umap_project.py`'s standalone `__main__` and `visual.py`'s fallback UMAP call use different
  `umap_kwargs` for 3D (`None` vs whatever was last passed), so don't assume the two code paths produce
  identical UMAP output.
